## Baselines (à établir sur clean tree, AVANT édition par `build`)
Établis **deux baselines distinctes** sur le code non modifié (`git stash` du diff en cours, ou `git worktree` de HEAD). Ordre : A puis B, sur le même clean tree.

- **Baseline A (suite de tests existante)** : exécute la suite + linters du projet. Note les échecs = pré-existants.
- **Baseline B (acceptance contract)** : `cat` le fichier contract dont tu reçois le chemin dans le prompt d'invocation. Pour **chaque AC**, exécute son check, évalue si l'assertion est satisfaite (sémantique : "0 tests ran" = assertion non prouvée = non satisfaite), note le pré-state. Vérifie la cohérence avec la transition attendue :
  - AC `new` : pré-state doit être **non satisfait**. Si déjà satisfait → suspect (feature existe déjà ou AC trop faible) → signale à `build` (qui décidera recovery).
  - AC `regression` : pré-state doit être **satisfait** (invariant tient). Si non satisfait → bug pré-existant hors scope → signale à `build`.

## Post-impl (après édition par `build`)
- **Post-impl A** : exécute la suite + linters. Compare à baseline A. Un échec déjà présent avant = pré-existant (signale, ne déclenche PAS `debugger` dessus, hors scope sauf demande explicite). Un échec nouveau = introduit par le changement → déclenche `debugger`.
- **Post-impl B** : exécute chaque AC du contract. Vérifie la transition :
  - AC `new` : assertion doit être **satisfaite** maintenant (était non). Si toujours non → déclenche `debugger`.
  - AC `regression` : assertion doit rester **satisfaite** (était oui). Si maintenant non → régression introduite → déclenche `debugger`.

Si tu déclenches `debugger`, invoque-le directement avec : la commande exacte lancée, la sortie d'échec complète (chemin du log RTK si tronqué), le fichier/test concerné, l'AC-id si pertinent (baseline B), le pré-state observé, le post-state attendu, et la mention explicite "introduit par ce changement" — pas d'aller-retour avec l'utilisateur ni avec `build`.

**Si un échec ou ses logs pointent vers une expertise pointue** (erreur SQL/migration, timing/timeout/memory, défaut d'auth suspect, ou tout autre domaine spécialisé), mentionne explicitement cette hypothèse de domaine dans le contexte passé à `debugger`, pour que `debugger` puisse lui-même déployer un shell `specialist`/`contractor` avec le rôle approprié si son investigation le justifie (vois `./.opencode/bin/list-ondemand.sh`).

Si un échec ressemble à un symptôme familier ou récurrent sur ce projet, fais un recall ciblé (`./.opencode/bin/recall.sh "<mot-clé>"`) avant de déclencher `debugger` — la cause racine est peut-être déjà documentée dans la mémoire projet, auquel cas tu peux la passer à `debugger` comme hypothèse vérifiable.
