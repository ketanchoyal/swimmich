# Task: change-password

> **Audit 2026-09-15 — écart G18** : le client Flutter expose un écran de changement de mot de passe (`ChangePasswordRoute` dans `mobile/lib/routing/router.dart`, page `mobile/lib/pages/login/change_password.page.dart`), migré sur le nouvel endpoint par le commit upstream `refactor: migrate to new changePassword endpoint (#31277)` ; côté iOS, `POST /api/auth/change-password` n'est appelé nulle part (`grep -rn "change-password" Sources/` → aucun résultat) alors que le serveur signale déjà l'obligation au client : `LoginResponseDto.shouldChangePassword` (`Sources/Core/Types/DTOs.swift:17`) est décodé à chaque login puis **jamais lu** (`grep -rn "shouldChangePassword" Sources/` ne renvoie que les définitions de DTO et un `nil` de payload dans `Sources/Features/Admin/AdminViewModel.swift:58`).

**Objectif** : après cette fiche, l'utilisateur connecté ouvre « Me » → section **Security** → « Change Password », saisit son mot de passe actuel, le nouveau (deux fois), coche ou non la déconnexion des autres appareils, et valide : le serveur applique le changement, l'app confirme et remet le drapeau `shouldChangePassword` à `false`. Quand le serveur signale `shouldChangePassword` à la connexion (mot de passe réinitialisé par un administrateur), la même section Security affiche un avertissement qui mène à cet écran ; l'utilisateur n'a jamais à repasser par le web Immich pour changer son mot de passe.

**Hors périmètre** :
- Le **PIN code** (`POST /api/auth/pin-code`, `POST /api/auth/pin-code/reset`) : c'est une seconde serrure distincte du mot de passe, l'écart n'est pas listé au backlog G18 et le dépôt n'a aucune surface PIN (l'app verrouille par `AppLockViewModel`, Face ID).
- La **réinitialisation du mot de passe par un administrateur** (`PUT /api/admin/users/{id}` avec `password`) : c'est l'écart admin, déjà porté par `AdminViewModel` (`Sources/Features/Admin/AdminViewModel.swift:58` envoie `shouldChangePassword: nil`).
- Le **mot de passe oublié / reset sans session** (le lien e-mail `immich://reset-password?token=…`) : le dépôt n'a aucun handler d'URL entrant (aucun `.onOpenURL` dans `Sources/`), donc rien à raccorder ici.
- Le déverrouillage de session (`POST /api/auth/session/unlock`) : c'est l'écart `device-sessions`, fiche sœur.
- La **traduction** des chaînes neuves au-delà de l'extraction automatique : aucune écriture manuelle dans `Resources/Localizable.xcstrings` (la clé est la chaîne anglaise).

**Hypothèses** (vérifiées dans le dépôt et contre `immich-app/immich@main` = `e55ac299`, le 2026-09-15) :

- **Upstream — l'écran et sa route** :
  - `mobile/lib/pages/login/change_password.page.dart` : la page Flutter du changement de mot de passe, atteinte par `ChangePasswordRoute` (`mobile/lib/routing/router.dart`) ; le commit `refactor: migrate to new changePassword endpoint (#31277)` est ce qui aligne le client sur le corps DTO décrit ci-dessous.
  - **Forme du contrat, côté serveur** : `server/src/services/auth.service.ts:128-150` — `changePassword(auth: AuthDto, dto: ChangePasswordDto)`. Ligne 131-134 : si le mot de passe actuel ne valide pas, le serveur jette `new BadRequestException('Wrong password')`, soit **HTTP 400, pas 401** — donc le handler global 401 de l'app (qui appelle `resetSession()`) **n'est pas** déclenché par une faute de frappe. Lignes 138-141 : le succès écrit `password` **et** `shouldChangePassword: false` sur l'utilisateur. Lignes 143-147 : l'événement `AuthChangePassword` porte `currentSessionId` + `invalidateSessions`, ce qui déconnecte les **autres** appareils (la session courante survit). Ligne 149 : la réponse est `mapUserAdmin(updatedUser)`.
  - **Contrat OpenAPI** (vérifié dans `/tmp/immich-openapi-main.json`) : clé de chemin `/auth/change-password`, méthode `POST`, `operationId: changePassword`, `security: [{bearer:[]},{cookie:[]},{api_key:[]}]`, `requestBody.content["application/json"].schema = ChangePasswordDto`, réponse `200` de schéma `UserAdminResponseDto`. `ChangePasswordDto` : `required: ["newPassword","password"]`, `password` = « Current password » (string), `newPassword` = « New password (min 8 characters) » (`minLength: 8`), `invalidateSessions` = `boolean`, `default: false`, description « Invalidate all other sessions ».
- **iOS — ce qui existe déjà et sert de couture** :
  - Protocole client : `Sources/Core/Protocols/ImmichClient.swift:21-23` porte `func login(email:password:) async throws -> LoginResponseDto`, `func logout() async throws -> LogoutResponseDto`, `func validateToken() async throws -> ValidateAccessTokenResponseDto`. Le commentaire de `:25` acte que l'échange OAuth renvoie « the same payload as `login` » — donc tout nouveau champ de session se lit aux deux points d'appel.
  - Implémentation : `Sources/Services/ImmichAPIClient.swift` — `login` (`:77-79`) écrit `sendNoAuth(.POST, path: ImmichAPI.auth.path("/login"), body: AnyEncodable(LoginCredentialDto(...)))`, `logout` (`:81-83`) écrit `sendAuthed(.POST, path: ImmichAPI.auth.path("/logout"))`. Les deux helpers génériques sont `sendAuthed` (`:684`) et `sendAuthedRaw` (`:689`, jette `APIError.unauthorized` si aucun token). L'enum de chemins `ImmichAPI` expose déjà le préfixe d'auth (`ImmichAPI.auth.path("/login")`) et le préfixe users (`ImmichAPI.users.path("")`, `:605`) — `ImmichAPI.auth.path("/change-password")` et `ImmichAPI.users.path("/me")` sont donc valides sans rien ajouter.
  - Réponse : `UserAdminResponseDto` **existe déjà** (`Sources/Core/Types/DTOs+Admin.swift:6`) et porte `var shouldChangePassword: Bool?` (`:14`) — aucun DTO de réponse à créer pour cet endpoint.
  - Drapeau serveur : `LoginResponseDto.shouldChangePassword: Bool` (`Sources/Core/Types/DTOs.swift:17`) est décodé mais ignoré par `AuthViewModel.applySession(token:email:name:userId:isAdmin:)` (`Sources/Features/Auth/AuthViewModel.swift:330`), appelé depuis le login (`:261`) et depuis OAuth (`:316`). Rien dans `Sources/` ne remonte ni ne consomme ce drapeau.
  - État d'auth : `AuthViewModel` (`:49-54`) expose `accessToken`, `userEmail`, `userName`, `userId`, `isAdmin`, `isAuthenticated` ; `logout()` (`:349`) et `resetSession()` (`:358`) sont les deux sorties de session. `isAdmin` est persisté (`:105`, clé `Self.isAdminDefaultsKey`) ; c'est le précédent de ce qui se persiste et de ce qui ne se persiste pas.
  - Surface : `Sources/Features/Profile/ProfileView.swift` — `NavigationStack` à `:25`, `@Environment(AuthViewModel.self) private var auth` à `:7`, section **Security** déjà présente à `:130-141` (elle contient `Toggle("Require Face ID")` avec `.accessibilityIdentifier("appLockToggle")` et un `footer` explicatif), section logout destructif à `:143-153`. La clé `Security` **existe déjà** dans `Resources/Localizable.xcstrings` — l'en-tête ne coûte aucune chaîne neuve.
  - Injection : `Sources/DependencyContainer.swift:81` fabrique `AuthViewModel` (`makeAuthViewModel()`), et `Sources/RootView.swift:234` instancie la feuille une seule fois, `ProfileView(trash:storage:upload:duplicates:people:tags:stacks:partners:admin:offline:notifications:language:)`, en passant **tous** les ViewModels explicitement (la feuille est pilotée par `@State private var showProfile`, `:114`).
  - DesignSystem : les trois couleurs dont l'écran a besoin existent déjà — `Color.immichError` (utilisée dans `ProfileView.swift:234`), `Color.immichSuccess` et `Color.immichWarning` (`Sources/DesignSystem/Tokens/ImmichColors.swift:42` et `:56`). Aucun token à créer.
- **Ce qui rend la fiche nécessaire** : `Sources/Features/Security/` n'existe pas, aucun `ChangePassword*` n'existe dans `Sources/`, et le drapeau `shouldChangePassword` est un champ mort — un utilisateur dont l'administrateur a réinitialisé le mot de passe ne voit aucun signal dans l'app.

**Approche retenue** : A — deux fichiers neufs dans `Sources/Features/Security/` (`ChangePasswordViewModel` `@MainActor @Observable` + `ChangePasswordView` stateless), deux méthodes ajoutées au protocole `ImmichClient` + `ImmichAPIClient`, un drapeau `shouldChangePassword` porté par `AuthViewModel` (rempli au login depuis `LoginResponseDto`, remis à `false` depuis la réponse `UserAdminResponseDto` du changement), une ligne `NavigationLink` posée **dans la section Security existante** de `ProfileView`.
- **B (rejetée)** : présenter la feuille de changement de mot de passe automatiquement au login quand `shouldChangePassword` est vrai, depuis `AuthenticatedRoot` → rejetée pour deux raisons mesurables. (1) `AuthenticatedRoot` porte déjà deux présentations concurrentes — la feuille `showProfile` (`RootView.swift:114,233-235`) et le plein écran de `AppLockViewModel` — et le dépôt n'a aucun précédent d'interstitiel post-login à séquencer avec elles. (2) Le drapeau n'est connu qu'à l'instant du login : `restoreSession()` (`AuthViewModel.swift:120`) ne relit pas `shouldChangePassword`, donc un administrateur qui réinitialise le mot de passe pendant une session active ne déclencherait jamais la feuille — l'avertissement deviendrait un événement unique et non rejouable, alors qu'il doit rester visible aussi longtemps que le serveur le dit.
- **C (rejetée)** : mettre `changePassword(currentPassword:newPassword:invalidateSessions:)` sur `AuthViewModel` et rendre le formulaire en ligne dans `ProfileView`, sans fichier neuf → rejetée pour deux raisons mesurables. (1) `AuthViewModel` (480 lignes) est l'état d'auth global observé par `RootView` : y stocker les trois champs d'un formulaire ferait re-rendre tout l'arbre à chaque frappe, et les ViewModels de `ProfileView` sont justement des instances d'écran fabriquées par le conteneur et passées explicitement (`RootView.swift:234` — `LanguageSettingsViewModel`, `OfflineDownloadViewModel`, `StorageStatsViewModel` suivent tous ce patron, un ViewModel par écran). (2) La feuille « Me » est un seul `Form` : un formulaire imbriqué à trois `SecureField` y partagerait le scroll du hub et son état d'erreur n'aurait aucun propriétaire naturel.

## Étapes

1. **Le DTO de requête** — EDIT `Sources/Core/Types/DTOs.swift` : sous `LoginCredentialDto` (`:5-8`), ajouter `struct ChangePasswordDto: Codable, Equatable { let password: String; let newPassword: String; let invalidateSessions: Bool }`. L'ordre des propriétés importe peu (encodage par clé), mais les trois noms doivent être exactement ceux de `ChangePasswordDto` dans l'OpenAPI — dont deux **required** : `password` et `newPassword`. Ne pas décoder la réponse dans un DTO neuf : `UserAdminResponseDto` existe déjà.
2. **La couture client** — EDIT `Sources/Core/Protocols/ImmichClient.swift` : après `func logout()` (`:22`), ajouter `func changePassword(currentPassword: String, newPassword: String, invalidateSessions: Bool) async throws -> UserAdminResponseDto`. Le retour n'est pas `Void` : c'est la réponse `200` du serveur, et c'est elle qui porte le `shouldChangePassword: false` posé par `auth.service.ts:140` — la seule preuve serveur que le drapeau est retombé.
3. **L'implémentation transport** — EDIT `Sources/Services/ImmichAPIClient.swift` : après `logout()` (`:81-83`), ajouter la méthode avec `try await sendAuthed(.POST, path: ImmichAPI.auth.path("/change-password"), body: AnyEncodable(ChangePasswordDto(password: currentPassword, newPassword: newPassword, invalidateSessions: invalidateSessions)))` — même forme que `login` (`:78`) et `logout` (`:82`), donc aucun nouveau cas dans l'enum `ImmichAPI` (`auth` et `users` existent déjà). Ajouter aussi, dans la section « Users » (`:600-606`), `func currentUser() async throws -> UserAdminResponseDto { try await sendAuthed(.GET, path: ImmichAPI.users.path("/me")) }` : c'est ce qui permet de relire le drapeau plus tard sans re-login, et le chemin est prouvé par `ImmichAPI.users.path("")` en `:605`. Aucun traitement spécial du 400 : `BadRequestException('Wrong password')` remonte en erreur normale, l'app n'a pas à intercepter un 401 sur cette route (vérifié `auth.service.ts:131-134`).
4. **Le ViewModel** — NEW `Sources/Features/Security/ChangePasswordViewModel.swift` : `import Foundation`, `import Observation`. `@MainActor @Observable final class ChangePasswordViewModel` avec `private let client: any ImmichClient`, `init(client: any ImmichClient)`.
   - Saisie : `var currentPassword = ""`, `var newPassword = ""`, `var confirmPassword = ""`, `var invalidateSessions = true` (le défaut de l'API est `false`, mais l'écran ne s'ouvre que pour remplacer un secret : l'utilisateur qui ne veut pas déconnecter ses autres appareils décoche — la question est posée, pas subie).
   - Validation **locale**, avant tout réseau : `var newPasswordTooShort: Bool { !newPassword.isEmpty && newPassword.count < 8 }` (la borne `minLength: 8` est celle du contrat), `var confirmationMismatch: Bool { !confirmPassword.isEmpty && confirmPassword != newPassword }`, `var newPasswordUnchanged: Bool { !newPassword.isEmpty && newPassword == currentPassword }`, et `var canSubmit: Bool { !isSubmitting && !currentPassword.isEmpty && newPassword.count >= 8 && newPassword == confirmPassword && newPassword != currentPassword }`.

## Incertitudes à lever à l'implémentation

- **Le nom du widget de formulaire upstream.** La page `mobile/lib/pages/login/change_password.page.dart` est vérifiée ; le widget de formulaire qu'elle monte ne l'est pas, et son découpage décide si l'upstream valide en local (`validator:`) ou laisse le serveur répondre. Vérifier par : `gh api repos/immich-app/immich/contents/mobile/lib/pages/login --jq '.[].name'` puis, sur le fichier de widget trouvé, `gh api repos/immich-app/immich/contents/mobile/lib/widgets/forms --jq '.[].name'`. Si l'upstream confirme le mot de passe par un second champ, l'étape 4 est déjà alignée ; s'il ne le fait pas, retirer `confirmPassword` de `canSubmit` serait une régression d'ergonomie — garder le champ.
- **Le message d'erreur d'un mot de passe actuel faux.** `auth.service.ts:133` jette `BadRequestException('Wrong password')` ; reste à savoir ce que `ImmichAPIClient` surface dans `errorMessage` (le message brut du serveur, ou un libellé `APIError` généré). Le VM affiche aujourd'hui `error.localizedDescription` tel quel. Vérifier par : `grep -n "localizedDescription\|case badRequest\|Wrong password" Sources/Core/Types/APIError.swift Sources/Services/ImmichAPIClient.swift`. Si `APIError` ne relaie pas le message serveur, mapper explicitement le 400 de cette route sur `String(localized: "That password is not right.")` — la clé existe **déjà** dans `Resources/Localizable.xcstrings` (vérifié) et est le libellé exact de l'échec d'un mot de passe.
