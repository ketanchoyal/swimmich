# Task: star-ratings

> **Audit 2026-09-15 — écart G7** (`.omp/backlog/ImmichSwiftUI-backlog.md` §2.17) : le client Flutter note un asset depuis le viewer — `mobile/lib/presentation/widgets/asset_viewer/asset_details/rating_details.widget.dart` (relu sur `main` le 2026-09-15) gate l'affichage sur la préférence serveur `ratingsEnabled` puis rend `RatingBar(initialRating: exifInfo?.rating?.toDouble() ?? 0, itemSize: 40, onRatingUpdate:, onClearRating:)`, qui appelle `actionProvider.updateRating(ActionSource.viewer, rating)` ; `rating_bar.widget.dart` (`RatingBar`, `itemCount = 5`) re-taper l'étoile courante renvoie `0` et déclenche `onClearRating`.
> Côté iOS, la note est **affichée morte** : `Sources/Features/PhotoViewer/PhotoInfoPanel.swift:305` produit la ligne `("star.fill", exif.rating.map { String($0) })` dans `ExifInfoPanel.exifItems`, et aucun appelant ne remplit jamais les deux champs d'écriture existants (`PhotoViewer.swift:742` et `TimelineViewModel.swift:135,147` n'envoient que `visibility: .archive`).
> *(Le hash épinglé `e55ac299` n'est pas présent dans le clone local — `git show e55ac299:<path>` sort 128 ; les deux widgets ont donc été relus en clair sur `main` le même jour, où les chemins existent.)*

**Objectif** : depuis le panneau de détails du viewer, l'utilisateur donne 1 à 5 étoiles à la photo courante (et retire la note en re-tapant l'étoile déjà active), avec persistance serveur immédiate ; et dans l'onglet Recherche, un filtre « Rating » restreint les résultats aux assets notés 1 à 5 étoiles, cumulable avec la requête texte et les filtres EXIF existants.

**Hors périmètre** :
- **Le rejet (`rating: -1`)** : l'API le porte (`AssetBulkUpdateDto.rating` : `minimum: -1`, description « -1 (rejected) »), mais aucune surface upstream n'est reprise ici (l'upstream ne fait que 1–5 + clear). L'UI n'écrit jamais `-1`.
- **La note en lot depuis la sélection de la timeline** : `TimelineViewModel.swift:135` sait déjà envoyer un `AssetBulkUpdateDto` ; l'ajouter à la barre de sélection est une fiche distincte (bande d'AC de la sélection multiple).
- **Le bucket « Unrated » du filtre de recherche** : voir l'approche C. Le filtre livré est « Any rating » + 1…5.
- **La migration des filtres plats vers `filter: SearchFilter`** (v3.2.0) : cross-cutting, elle concerne les 33 champs plats déjà utilisés par `SearchViewModel.dispatchSearch`.
- **Le swipe-de-note sur les tuiles de la timeline** (geste Flutter absent du client iOS comme de cette fiche).
- **La préférence serveur `ratingsEnabled`** : l'upstream masque la barre si la préférence l'interdit ; iOS ne lit aucune préférence utilisateur aujourd'hui (voir Incertitudes).

**Hypothèses** (vérifiées dans le dépôt et contre `immich-app/immich@main`, le 2026-09-15) :
- **La lecture existe déjà** : `ExifResponseDto.rating: Int?` (`Sources/Core/Types/DTOs.swift:162`) est la seule source de lecture de la note dans l'app, et `PhotoInfoPanel.swift:305` la consomme — il ne manque que le canal d'écriture.
- **Les deux porteurs d'écriture existent dans les DTO locaux** :
  - `UpdateAssetDto.rating: Int?` (`Sources/Core/Types/DTOs.swift:238-247`, aux côtés de `isFavorite`, `dateTimeOriginal`, `latitude`/`longitude`) ;
  - `AssetBulkUpdateDto.rating: Int?` (`Sources/Core/Types/DTOs.swift:255-266`) — générés depuis l'OpenAPI, donc alignés sur le serveur.
- **Le contrat mono-asset rend le corps de réponse** : `func updateAsset(id: String, dto: UpdateAssetDto) async throws -> AssetResponseDto` (`Sources/Core/Protocols/ImmichClient.swift:48`), implémenté `sendAuthed(.PATCH, path: ImmichAPI.assets.path("/\(id)"), body: AnyEncodable(dto))` (`Sources/Services/ImmichAPIClient.swift:151`).
- **Le contrat bulk, lui, jette la réponse** : `func bulkUpdateAssets(dto: AssetBulkUpdateDto) async throws` (`ImmichClient.swift:252`) → `_ = try await sendAuthedRaw(.PUT, path: ImmichAPI.assets.path(""), …)` (`ImmichAPIClient.swift:596-598`), et l'OpenAPI décrit `PUT /assets` comme « Updates multiple assets at the same time » sans `AssetResponseDto`.
- **Le propriétaire des mutations d'un asset est déjà en place** : `AssetDetailViewModel` (`Sources/Features/AssetDetail/AssetDetailViewModel.swift:5-6`, `@Observable final class`) expose `toggleFavorite()`, `setDateTime(_:)`, `setLocation(latitude:longitude:)`, avec les crochets de test `private(set) var lastUpdateBody: UpdateAssetDto?` / `lastUpdateAssetId` (précédent AC-010).
- **Le motif optimiste-et-revert est déjà écrit dans le dépôt** : `PhotoViewer.toggleFavorite` (`PhotoViewer.swift:717-729`) écrit l'état local, appelle le serveur, et restaure la valeur d'origine sur `catch` (« UI never lies about server state »).
- **Aucun paramètre neuf n'est nécessaire pour la carte** : `PhotoInfoPanel` reçoit déjà `let vm: AssetDetailViewModel?` (`:5`) et sait ne rien rendre sans lui (les feuilles `AdjustLocationSheet`/`AdjustDateSheet` sont gardées par `if let vm`).
- **L'encodeur synthétisé ne peut pas dé-noter** : `UpdateAssetDto` et `AssetBulkUpdateDto` déclarent `rating` en `Int?` sans `encode(to:)` custom, donc `nil` **omet la clé** au lieu d'envoyer `null` ; `0` et `-1` sont invalides depuis v3 côté serveur (voir ci-dessous).
- **Le contrat serveur de la note** (`/tmp/immich-openapi-main.json`) :
  - `PUT /api/assets` → `AssetBulkUpdateDto.rating` : `minimum: -1`, `maximum: 5`, `nullable`, `x-immich-state: "Stable"`, description « Rating in range [1-5] (starred), -1 (rejected), or null (unrated) », historique `v1 Added` → `v2 Stable` → `v3 Updated` (« Using 0 as a rating is no longer valid. »).
  - Donc trois états valides seulement — 1…5, `-1`, `null` — et **aucun** moyen d'écrire « 0 » pour effacer.
- **Le filtre serveur existe mais est déprécié pour cause de refonte globale** : `POST /api/search/metadata` → `rating` (`minimum: 1`, `maximum: 5`, `nullable`, description « Filter by rating [1-5], or null for unrated ») est `deprecated: true` / `x-immich-state: "Deprecated"` depuis **v3.2.0**.
  - La dépréciation n'est **pas** propre à `rating` : les 33 autres champs plats du même schéma le sont aussi (`isFavorite`, `albumIds`, `city`, `make`, `model`, `visibility`, `ocr`, `page`, `size`… tous `x-immich-state: "Deprecated"`).
  - Le remplacement est `filter: SearchFilter`, ajouté en `v3.2.0`, dont `rating` est un `NumberFilterNullable` (`eq`, `ne`, `gt`, `lt`, `in`, …).
  - Implication honnête : livrer le champ plat aujourd'hui est **cohérent** avec les cinq filtres déjà envoyés par l'app et ne peut pas régresser ; la dette réelle (négociation de version serveur + `SearchFilter`) est transversale et sort de cette fiche.
- **Le point d'insertion du filtre est unique** : `MetadataSearchDto` (`Sources/Core/Types/SearchDTOs.swift:8-23`) ne porte pas `rating` ; `dispatchSearch(page:)` (`Sources/Features/Search/SearchViewModel.swift:315-328`) construit `MetadataSearchDto(query:page:)` puis y applique `pendingExploreFilter`.
- **Une recherche sans texte est légitime** : `search()` (`SearchViewModel.swift:167-212`) ne court-circuite jamais sur requête vide — c'est ainsi que `searchByExplore` filtre par ville avec `query == ""`.
- **Le mode Smart ignore tout filtre** : `SmartSearchDto` (`SearchDTOs.swift:26-31`) n'a que `query`/`page`/`size`/`withExif` ; un filtre de note y serait silencieusement perdu.
- **Le mode Metadata est déjà le mode « filtres »** : `SearchView.swift:138-151` porte `searchModeMenu` dans le `ToolbarItemGroup(.topBarTrailing)`, à côté du bouton `bookmark` de sauvegarde.
- **L'état vide existe déjà et se réutilise** : `SearchView.resultsContent` (`:180-190`) rend `ContentUnavailableView("No results", systemImage: "magnifyingglass", description: Text("Try a different search term."))` dès `hasSearched` — un filtre de note sans résultat tombe donc dans un état déjà localisé, sans chaîne neuve.
- **Le type de corps universel du client est `AnyEncodable`** : `Sources/Core/Types/AnyEncodable.swift:4`, utilisé partout (`sendAuthed(.PATCH, path: …, body: AnyEncodable(dto))`) — il accepte un type neuf comme `RatingUpdateDto` sans modification.
- **L'upstream a six états de filtre, dont un inexprimable ici** : `mobile/lib/widgets/search/search_filter/star_rating_picker.dart` (relu sur `main`) rend six `RadioListTile<int>` (`value: index`, libellés `context.t.rating_count(count: index)`) et replie la valeur sur `SearchRatingFilter(rating: Option.some(newValue == 0 ? null : newValue))` — l'index `0` désigne « aucun filtre » **ou** « non noté » selon le repli, ce qui montre que l'upstream lui-même n'écrit le `null` que par un `Option`.
- **Le repli exact n'est pas transposable en Swift sans wrapper** : un `Int?` nil ne se distingue pas d'un champ absent à l'encodage (voir hypothèse sur l'encodeur), d'où le choix explicite de l'étape 8 : 1…5 + « Any rating », le bucket « unrated » restant hors périmètre.
- **Le domicile d'un composant générique est le DesignSystem** : `Sources/DesignSystem/Components/` héberge les atomes partagés nommés `PV*` (`PVStatusBadge.swift`, `PVInputGroup.swift`, `PVGridCell.swift`, `PVHeaderBadge.swift`…).
- **La carte ne peut pas s'afficher avant la donnée** : `PhotoInfoPanel.content` ne rend rien tant que `vm?.detail?.exifInfo` est absent (il bascule alors sur l'erreur ou un `ProgressView`) — la barre lit donc toujours une note déjà chargée depuis le serveur, et aucun état « note inconnue » n'est à gérer.
- **Noter ne change pas l'appartenance à une grille** : aucun `onDataChanged` n'est câblé depuis la carte (le câbler ferait relancer la recherche complète de l'onglet à chaque tap, `SearchView.swift:96-100`). Les grilles déjà chargées gardent donc leur contenu après une note — conséquence assumée.
- **Le rafraîchissement de `detail` est déjà dans le corps de réponse** : le PATCH rend l'`AssetResponseDto` à jour (`ImmichClient.swift:48`), ce qui évite un `getAsset` supplémentaire et alimente `exifInfo.rating` en un aller-retour.
- **Les fichiers de test à étendre existent** : `Tests/AssetDetailViewModelTests.swift`, `Tests/DTOEncodingTests.swift`, `Tests/SearchViewModelTests.swift`, `Tests/Mocks/MockImmichClient.swift` — aucun fichier de test neuf n'est justifié.
- **Ce qui rend la fiche nécessaire** : `grep -rn "rating" Sources/` ne montre aucun chemin d'écriture rempli, et `grep -rn "rating" Sources/Features/Search/` est vide — le `MetadataSearchDto` construit par le ViewModel ne peut pas exprimer le filtre.

**Approche retenue** : A — l'écriture passe par **PATCH `/api/assets/:id`** (`UpdateAssetDto.rating`), via une méthode dédiée `setAssetRating(id:rating:)` sur `ImmichClient` et un corps `RatingUpdateDto` qui sait encoder un **`null` explicite** (`rating: null` = non noté), parce que l'encodeur synthétisé de `UpdateAssetDto` **omet** un `Int?` nil (donc ne peut pas dé-noter) et que `0`/`-1` sont invalides depuis v3 ; l'UI du viewer est un `PVRatingBar` réutilisable, et le filtre de recherche est le champ plat `rating` d'`MetadataSearchDto`, piloté par un `Menu` qui force le mode Metadata.
- **B (rejetée)** : réutiliser `bulkUpdateAssets(dto: AssetBulkUpdateDto)` (`ImmichClient.swift:252`, `PUT /api/assets`) → mesurablement pire sur deux points :
  - l'implémentation jette le corps (`_ = try await sendAuthedRaw(.PUT, …)`, `ImmichAPIClient.swift:596-598`) et la route ne rend pas d'`AssetResponseDto`, donc rafraîchir `detail.exifInfo.rating` après chaque tap coûterait un `getAsset(id:)` supplémentaire par étoile ;
  - `AssetBulkUpdateDto.rating` est lui aussi un `Int?` (`DTOs.swift:263`) : le problème du `null` explicite reste entier, l'alternative n'achète donc rien et perd la réponse.
- **C (rejetée)** : porter tout le filtre par le chemin moderne `filter: { rating: NumberFilterNullable }` pour couvrir en plus le bucket « Unrated » → rejetée sur trois faits :
  - les cinq filtres voisins du même écran (`pendingExploreFilter` → `city`/`make`/`model`/`country`/`state`/`lensModel`, `SearchDTOs.swift:8-23`) restent plats : le même corps de requête porterait deux conventions ;
  - `NumberFilterNullable.eq` est `nullable: true`, donc « `eq: null` » souffre exactement du même trou d'encodage que le champ plat et exigerait un **second** wrapper null-preserving pour un seul contrôle ;
  - `SearchFilter` n'existe que depuis v3.2.0, donc l'écrire sans négociation de version promet un 400 sur les serveurs plus anciens.

## Incertitudes à lever à l'implémentation

- **L'état OpenAPI de `UpdateAssetDto.rating` (PATCH mono-asset) vs celui d'`AssetBulkUpdateDto.rating` (PUT).** Le champ du bulk est `Stable` ; celui du PATCH n'a pas été relu. Trancher par : `python3 -c "import json;d=json.load(open('/tmp/immich-openapi-main.json'));print(d['components']['schemas']['UpdateAssetDto']['properties']['rating'])"` — s'il est absent ou déprécié, basculer l'étape 4 sur `PUT /api/assets` en acceptant le `getAsset` supplémentaire après écriture.
- **La préférence serveur `ratingsEnabled`.** L'upstream masque la barre quand la préférence utilisateur l'interdit (`userMetadataPreferencesProvider`) ; iOS n'a aucune lecture de préférences. Trancher par : `python3 -c "import json;d=json.load(open('/tmp/immich-openapi-main.json'));print([p for p in d['paths'] if 'preference' in p])"` — si une route existe, la lire avant d'afficher la carte ; sinon la carte s'affiche inconditionnellement et cela doit être assumé explicitement.
- **La valeur `-1` en lecture.** `exifInfo.rating` peut valoir `-1` (asset rejeté) : la barre l'afficherait comme « non noté » (0 étoile) et une re-note écraserait le rejet. Trancher par `curl -s -H "x-api-key: $KEY" "$IMMICH/api/assets/$ID" | jq '.exifInfo.rating'` sur un asset rejeté, puis décider : carte en lecture seule avec un libellé « Rejected », ou écrasement assumé et documenté dans l'UI.
- **Le serveur accepte-t-il `PATCH /api/assets/:id {"rating": null}` et rend-il `exifInfo.rating: null` ?** L'OpenAPI le déclare `nullable`, le handler n'est pas prouvé. Trancher par : `curl -s -X PATCH -H "x-api-key: $KEY" -H 'Content-Type: application/json' -d '{"rating":null}' "$IMMICH/api/assets/$ID" | jq '.exifInfo.rating'`.
- **Le retour visuel pendant l'aller-retour.** Une étoile tapée part en PATCH : un tap rapide sur 1 puis 5 peut produire deux requêtes concurrentes.
