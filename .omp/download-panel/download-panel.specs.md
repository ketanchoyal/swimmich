# Task: download-panel

> **Audit 2026-09-15 — écart G10** : le client Flutter a une file de téléchargement persistante, avec panneau flottant et écran d'information dédié, adossée à l'URLSession de fond (`background_downloader`) ; côté iOS, `grep -rn "DownloadState\|downloadState\|taskProgress" Sources/` ne renvoie rien : il n'existe ni file, ni panneau, ni écran, et la seule écriture disque « hors ligne » est l'épinglage de cache (`Sources/Services/OfflineAssetStore.swift`).

**Objectif** : après cette fiche, l'utilisateur lance le téléchargement d'un original depuis le viewer — ou d'une sélection entière depuis la grille — et suit l'avancement sans rester sur l'écran qui l'a lancé : un panneau flottant apparaît au-dessus de la barre d'onglets, affiche la progression agrégée (n sur N, octets reçus), reste visible d'un onglet à l'autre, et ouvre un écran d'information où chaque fichier a sa ligne (nom, taille, barre, statut) avec les actions « annuler », « réessayer », « effacer les terminés ». Les fichiers arrivent nommés comme sur le serveur, dans un dossier que l'utilisateur retrouve, et ne sont jamais évincés par le budget du cache.

**Hors périmètre** :
- **L'épinglage hors ligne** (`Download for Offline` du viewer, `OfflineAssetsView`, `maxCacheSize`) : déjà livré, et volontairement distinct (voir approche B). La fiche ne touche ni `OfflineAssetStore` ni son budget.
- **L'export d'un asset vers Photos** : `SaveToLibraryViewModel.downloadOriginal()` (`Sources/Features/PhotoViewer/SaveToLibraryViewModel.swift:93`) garde son chemin (fetch en mémoire + `PHPhotoLibrary`). Le panneau couvre l'autre intention : « je veux le fichier », pas « mets-le dans ma pellicule ».
- **La lecture vidéo en flux** : `GET /assets/{id}/video/playback` (m3u8) sert le lecteur, pas le téléchargement — l'original vidéo passe par `GET /assets/{id}/original`, comme le fait déjà `SaveToLibraryViewModel`.
- **`POST /asset-files/{id}/download`** : route des *external libraries* (l'asset-file n'est pas dans la photothèque du serveur). Aucune surface iOS ne liste les asset-files aujourd'hui.
- **Le téléchargement par lien partagé public** (`key` / `slug` en query sur les deux routes de lot) : c'est une autre session, déjà tranchée par le viewer public.
- **Le choix du dossier de destination** et le regroupement automatique par album : l'upstream laisse `background_downloader` décider ; ici l'écran montre la file, pas une arborescence.

**Hypothèses** (vérifiées dans le dépôt et contre `immich-app/immich@main` = `e55ac299`, le 2026-09-15) :

- **Upstream — le modèle d'état de la file** : `mobile/lib/models/download/download_state.model.dart` définit
  - `DownloadInfo { fileName: String, progress: double, status: TaskStatus }` — une ligne de la file est donc **clé par asset** et porte trois choses : un nom, une fraction, un statut ;
  - `DownloadState { downloadStatus: TaskStatus, taskProgress: Map<String, DownloadInfo>, showProgress: bool }` — un statut global, la carte par asset, et un booléen d'affichage de progression (c'est le panneau flottant) ;
  - `TaskStatus` vient de `background_downloader` : la file du Flutter est une file **d'URLSession de fond**, pas une boucle au premier plan.
- **Upstream — la surface** : `mobile/lib/pages/common/download_panel.dart` (le panneau), `mobile/lib/presentation/pages/download_info.page.dart` (l'écran d'information), `mobile/lib/presentation/widgets/action_buttons/download_status_floating_button.widget.dart` (le bouton flottant). Les trois sont présents à la révision `e55ac299`.
- **Upstream — les deux chemins de téléchargement** :
  - **Mono-asset** : `GET /api/assets/{id}/original` (et `GET /api/assets/{id}/video/playback`, qui rend un m3u8 de flux). C'est le chemin déjà emprunté par `SaveToLibraryViewModel`.
  - **Lot** : il **existe** bien une route de téléchargement en lot, en **deux temps**.
    - `POST /download/info` (`operationId: getDownloadInfo`, body `DownloadInfoDto { albumId?, assetIds?, … }`) répond `DownloadResponseDto { archives: [DownloadArchiveInfo], totalSize }` avec `DownloadArchiveInfo { assetIds: [uuid], size }` : le serveur découpe lui-même la demande en N archives (plafond de taille/temps) et donne le **volume total**.
    - `POST /download/archive` (`operationId: downloadArchive`, body `DownloadArchiveDto { archiveName: String, assetIds: [uuid], edited: Bool }`, réponse `application/octet-stream`) renvoie le ZIP — la description du contrat précise « assets must have been previously requested via the getDownloadInfo endpoint », donc l'appel d'info est **obligatoire**, pas indicatif.
    - Les deux routes acceptent en query `key` et `slug` : le lot est aussi disponible depuis un lien public (hors périmètre).
- **iOS — la plomberie de transfert existe déjà et n'est pas sur le protocole client** :
  - `protocol FileDownloadTransport: Sendable` (`Sources/Core/Protocols/FileDownloadTransport.swift:24`) expose `func download(_ request: URLRequest, onProgress: @escaping @Sendable (Int64, Int64) -> Void) async throws -> DownloadedFile`, et renvoie des métadonnées HTTP (`statusCode`, `contentType`) séparées des octets « so the caller — not the transport — owns the policy ».
  - `struct URLSessionFileDownloadTransport: FileDownloadTransport` (`Sources/Services/URLSessionFileDownloadTransport.swift:8`), `let session: URLSession` (`:9`), `init(session: URLSession = .shared)`. Il appelle `URLSession.download(for:delegate:)` : les octets passent par un fichier temporaire système, jamais par un `Data` en mémoire — c'est la contrainte qui rend un ZIP de plusieurs Go survivable.
  - Le `ProgressDelegate` (`URLSessionFileDownloadTransport.swift:26+`) est **privé** et traduit `didWriteData / totalBytesWritten / totalBytesExpectedToWrite` en `onProgress(received, expected)` ; il est `@unchecked Sendable` et appelé sur la queue d'URLSession. Le panneau lit exactement cette paire, donc la remontée vers `MainActor` est à la charge de l'appelant (même couture que `BackupEngine.applyExportState`, mémo `72a1dbc8`).
  - `AssetFileTransfer` (`Sources/Services/AssetFileTransfer.swift`) est la **seule** mise en forme de noms du dépôt : `fileExtension(forMime:)` (table MIME → extension, repli `jpg`), `baseName(originalName:datePrefix:)` (nom serveur sans extension, repli `Photo-yyyy-MM-dd`), `writeTempFile(data:name:)` (dossier temporaire unique pour que le basename reste le vrai nom), `fetchData(from:token:session:)`.
  - **`ImmichClient` ne porte aucune méthode de téléchargement** : `grep -n "func .*[Dd]ownload" Sources/Core/Protocols/ImmichClient.swift` est vide. Les téléchargements d'aujourd'hui passent par `AssetFileTransfer.fetchData` (viewer) ou par le couple `URLRequest` + transport (cache hors-ligne). La file doit donc obtenir sa requête du client et la confier au transport.
  - Ce découpage est déjà celui du cache : `OfflineAssetStore` (`actor`) reçoit `transport: any FileDownloadTransport` par injection (`Sources/Services/OfflineAssetStore.swift:93`, init `:107-117`, `transport ?? URLSessionFileDownloadTransport()`).
- **iOS — l'état et la progression existants, à imiter et non à dupliquer** :
  - `OfflineDownloadViewModel` (`@MainActor @Observable`, `Sources/Features/Offline/OfflineDownloadViewModel.swift`) tient déjà `private var progressByID: [String: Double]` et `private var downloadingIDs: Set<String>`, exposés par `func isDownloading(_ assetID: String) -> Bool` et `func progress(for assetID: String) -> Double?` (commentaire : « 0...1 while downloading, `nil` when idle or when the server sent no `Content-Length` »), avec `func downloadAsset(_ asset: AssetReactItem, baseURL: URL, token: String?) async`, `func removeFromOffline(_:)`, `func setMaxCacheSize(_:)`, `func clearError()`. **Ces noms et cette convention de `nil` = barre indéterminée sont le vocabulaire à reprendre à l'identique.**
  - Ce VM reçoit ses identifiants **par appel** (`baseURL`, `token`) et non à la construction, parce qu'il est bâti dans le conteneur « long before a server is connected » : même contrainte pour la file.
  - `SaveToLibraryViewModel` (`Sources/Features/PhotoViewer/SaveToLibraryViewModel.swift:19`) est `@Observable`, construit **par présentation** du viewer (`PhotoViewer.swift:945` : `SaveToLibraryViewModel(asset:client:baseURL:token:)` dans un `.task`), consommé par `SaveSection` (`:1160`) via `Task { await saveVM.downloadOriginal() }` (`:1180`) ; il expose `isDownloading` et `errorMessage`. Il meurt avec la sheet.
  - `DependencyContainer` (`Sources/DependencyContainer.swift`) tient les dépendances process-wide : `let upload: UploadViewModel` avec le commentaire « One VM, one run, one island » (`:36`), et la famille `func make<Feature>ViewModel()` (`:81` `makeAuthViewModel` … `:205` `makeDuplicatesViewModel`), dont `makeOfflineDownloadViewModel()` qui partage `offlineStore` + `offlineIndex`.
- **iOS — la surface d'accueil d'un panneau flottant** : `Sources/RootView.swift` porte déjà
  - un précédent d'**overlay conditionnel global** : le doc-comment de tête (`:5`, « When app lock is enabled + locked, overlays a LockView ») et `private struct LockView` (`:273`) ;
  - trois `@State` de présentation (`showCreateAlbum` `:112`, `showCreateSharedLink` `:113`, `showProfile` `:114`) branchés en `.sheet` (`:221`, `:224`, `:233`) — le patron pour ouvrir l'écran d'information.
  - Une surimpression ancrée en bas est donc une construction déjà présente dans la vue racine, pas une nouveauté d'architecture.
- **iOS — la sélection de masse existe** : `AssetMultiSelectGrid` (`Sources/Features/Timeline/AssetMultiSelectGrid.swift:13`) prend `let assets: [AssetReactItem]`, `let selectedIds: Set<String>`, `let isLoading: Bool` ; son doc-comment (`:12`) précise que « sheet is responsible for having opened the flow (`beginPicking`) », donc l'action de masse appartient au détenteur de `selectedIds`.
- **Ce qui rend la fiche nécessaire** : `Sources/Features/DownloadPanel/` n'existe pas (`ls` → « No such file or directory ») ; le seul bouton de téléchargement du viewer s'appelle `downloadForOfflineButton` (`PhotoViewer.swift:1257`) et écrit dans le cache sous `CachedAssetInfo.fileName`, **dérivé de l'id d'asset** (`OfflineAssetStore.swift:32-40` : « Derived from the asset id so a re-download always lands on the same path — the asset id is unique and filesystem-safe; the server's name is not »). L'utilisateur ne peut donc aujourd'hui récupérer un fichier nommé `IMG_0421.HEIC` par aucun chemin.

**Approche retenue** : A — une file de téléchargement **process-wide** `DownloadQueueViewModel` (`@MainActor @Observable`), construite une fois par `DependencyContainer` comme `UploadViewModel`, qui possède sa propre liste de `DownloadItem` et s'appuie sur les briques existantes : `FileDownloadTransport` pour le streaming disque, `AssetFileTransfer` pour les noms, `ImmichAPIClient` pour les `URLRequest` et pour `POST /download/info`. Le panneau est une vue stateless posée en overlay dans `AuthenticatedRoot`, qui présente l'écran d'information.
- **B (rejetée)** : étendre `OfflineDownloadViewModel` et réutiliser son `progressByID` comme état du panneau → rejetée sur trois points mesurables.
  - **Destination** : `OfflineAssetStore` écrit sous `Application Support/OfflineAssets/` un fichier nommé `<assetId>.<ext>`, délibérément pas le nom du serveur (`OfflineAssetStore.swift:32-40`) ; un téléchargement utilisateur doit porter `IMG_0421.HEIC` (`AssetFileTransfer.baseName`).
  - **Durée de vie** : `setMaxCacheSize(_:)` élague le cache et `clearAll()` (`:152`) purge tout — un fichier que l'utilisateur vient de demander ne doit pas disparaître sur changement de budget.
  - **Unicité** : ce VM alimente le badge timeline via `OfflineAssetIndex` ; y faire passer les téléchargements ferait briller le badge « hors ligne » pour des fichiers jamais épinglés.
- **C (rejetée)** : donner à `SaveToLibraryViewModel` une extension « file d'attente » et l'appeler depuis le viewer → rejetée parce que ce VM est créé **par présentation** (`PhotoViewer.swift:945`, dans le `.task` de la sheet) et détruit à sa fermeture : une file qui meurt quand on quitte le viewer est exactement le défaut que l'écart décrit. De plus il ne connaît qu'un `asset`, jamais une sélection, et son chemin est « vers Photos », pas « vers un fichier ».

## Étapes

## Incertitudes à lever à l'implémentation

- **La session de téléchargement survit-elle à la suspension de l'app ?** `URLSessionFileDownloadTransport` prend `session: URLSession = .shared` (`Sources/Services/URLSessionFileDownloadTransport.swift:9`) : une file lancée puis l'app mise en arrière-plan s'arrête. L'upstream s'appuie sur `background_downloader` (URLSession de fond + reprise), ce qui est la vraie raison d'être du panneau flottant. Trancher par : `grep -rn "background(withIdentifier\|URLSessionConfiguration.background" Sources/` — si rien, décider explicitement entre une session de fond dédiée (identifiant, `handleEventsForBackgroundURLSession`, réconciliation au lancement) et une file « premier plan seulement » documentée comme telle. Ce choix ne change que l'étape 8.
- **La construction de l'URL d'original est-elle déjà centralisée ?** `SaveToLibraryViewModel.downloadOriginal()` (`:93`) et `OfflineDownloadViewModel.downloadAsset(_:baseURL:token:)` construisent chacun leur requête. Trancher par : `grep -rn "assets/\\\\?(\|/original" Sources/Services/ Sources/Features/PhotoViewer/` — si un helper existe, `originalRequest(assetId:)` (étape 3) doit **l'appeler** au lieu d'en écrire un troisième.
- **`AssetReactItem` porte-t-il le nom de fichier du serveur ?** Les étapes 1 et 4 supposent que `fileName` arrive du caller. `CachedAssetInfo.originalFileName` est un `String?` optionnel et son commentaire dit qu'il sert « for display and search » — signe que la timeline ne le transporte pas toujours. Trancher par : `grep -n "originalFileName" Sources/Core/Types/*.swift Sources/Features/Timeline/*.swift` — s'il manque, `enqueue(assets:)` doit lire le nom depuis la réponse de `downloadInfo` ou l'en-tête `Content-Disposition` remonté par `DownloadedFile`, avec repli sur `AssetFileTransfer.baseName(originalName: datePrefix:)`.
- **La destination exacte des fichiers.** L'étape 4 dit « vers la destination » sans la nommer : `AssetFileTransfer.writeTempFile` écrit dans `NSTemporaryDirectory()`, que l'OS évince — inadapté à un téléchargement que l'utilisateur veut garder.
